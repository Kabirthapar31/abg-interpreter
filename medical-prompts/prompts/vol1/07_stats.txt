# 1.7 | Sample size & statistics | Deciding your test after seeing your data is how p-hacking happens by accident. Plan the analysis before data collection, and verify every number AI gives you.

@@ M | sap-master | Pre-specified statistical analysis plan
aud: PG Resident
use: Write the plan before data collection. Run the analysis after the database is locked.
why: A pre-specified statistical analysis plan protects your integrity and your viva. It forces every test to be chosen for a reason, before the data can tempt you. It also becomes the analysis section of your thesis.
persona: You are a biostatistician with two decades of experience in clinical research who routinely explains statistical reasoning to clinicians. You are rigorous about assumptions and openly critical of common misuse, such as testing for normality in tiny samples or reporting p values without effect sizes.
context: Design: [prospective cohort / RCT / cross-sectional / diagnostic accuracy / before-after]
Total sample size, and per group if applicable: [N; n1, n2]
Primary objective: [state]
Secondary objectives: [list]
Software: [SPSS / R / Stata / GraphPad / Jamovi / Python]
My statistical comfort level: [beginner / intermediate / advanced]
My variables, each with name, type and role (example format: "FEV1 % predicted, continuous, baseline and 12 weeks, primary outcome"): [LIST ALL VARIABLES]
task: 1. Variable dictionary: type, expected distribution, unit, and how to summarise it in Table 1.
2. Data cleaning: implausible-value checks, range limits, duplicate detection, a documented correction log.
3. Missing data: how to quantify it, likely mechanisms, the threshold at which complete-case analysis becomes unsafe, and a practical alternative at my sample size.
4. Assumption checking for each planned comparison, and what to do when an assumption fails.
5. Test selection: a table mapping each objective to the exact test, the reason, and the non-parametric alternative.
6. Effect measures with confidence intervals for every comparison.
7. Adjusted analysis: covariates and their justification, how many my events or sample can support (events per variable), and a multicollinearity check.
8. Subgroup and sensitivity analyses, labelled exploratory.
9. Multiplicity: whether correction is needed, and the method.
10. Runnable, commented syntax in my software for every analysis.
11. Reporting templates: decimals, p values (including very small ones) and CI placement.
12. Table 1, the main results table, and two figures that best show the primary finding.
13. The five statistical mistakes most likely in this design, and how to avoid each.
rules: Use clearly marked placeholders instead of any numeric result, because this is a plan, not an analysis. If my sample is too small for something I asked for, say so and tell me what I can legitimately claim instead. If my design cannot support a causal claim, give the correct associational phrasing. Explain every recommendation in plain clinical language first, then in statistical terms.
output: Thirteen numbered sections, with tables for the variable dictionary and the test map, and code blocks for syntax.
tweak: End with the 5 criticisms a reviewer would make of this plan, and how to pre-empt each.
tips:
- Lock and date this plan before you unblind or begin analysis. Attach it to your thesis appendix.
- Run the syntax on 10 dummy rows first. Errors are easier to fix before the real data arrives.
- Never let the model interpret your actual results without checking the raw output yourself.

2. Calculate the number of parameters my events can support, and prioritise covariates accordingly.
3. Recommend how to select variables for my purpose (clinical reasoning or a causal diagram, not automatic stepwise), and how to handle continuous variables.

- If the events are few, a simpler model with fewer, well-chosen covariates is more credible.

why: Statistical output is full of numbers you don't need, and a few you absolutely do. Misreading which p value or estimate matters is common and costly. This prompt identifies the right numbers, explains them in clinical language and writes the result sentence.
persona: You are a biostatistics tutor who explains software output line by line to clinicians and writes results exactly as journals expect.
context: Software and test run: [e.g. SPSS independent-samples t-test]

Sample size I expected in this analysis: [n per group]
What I expected to find, before running it: [brief]
The output (copy as text or upload a screenshot): [PASTE OUTPUT HERE]
task: 1. Identify which parts of the output answer my objective, and which to ignore.
2. Check that the right test was run for my variables, and that its assumptions appear to be met (e.g. Levene's test, expected counts).
3. Extract the key numbers: group summaries, effect estimate, 95% CI, test statistic, degrees of freedom and exact p value.
4. Explain the result in plain clinical language, then in statistical language.
5. Write the result sentence for my results section in journal style.
6. Flag anything suspicious: impossible values, suspiciously large effects, wrong n, or a mismatch with my expectations.
7. Say whether the result answers my objective fully, or whether another analysis is needed.
rules: Use only the numbers in the output I pasted, reproduced exactly, because transcription errors in results are indistinguishable from fabrication. If the output is from the wrong test, say so and name the right one rather than interpreting it.
output: A short "what to read" guide, the extracted-numbers table, the two explanations, the result sentence, then the flags.
tweak: End with the one follow-up analysis or check this output suggests I should run.
tips:
- Always check that n in the output matches the n you expect. Missing data silently drops cases.
- Paste the output as text where possible. Screenshots can be misread.
- Keep a results log: output file, date, and the sentence you wrote from it.
